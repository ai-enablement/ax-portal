# 6단계 진행 및 승인 게이트

- 업무 6단계: 요구 접수 / 타당성 평가 / 요구 정의 / 설계 / 개발·평가 / 배포·확산.
- G1은 FEA 뒤, G2는 ARD 뒤, G3는 개발·평가 뒤, G4는 파일럿 뒤에 표시한다. 운영 이관은 별도 연결이다.
- 기존 DB 단계 코드와 문서 인덱스는 보존한다. DES 위치(5)의 설계/개발·평가는 deliveryPhase로 구분한다. 단계 재번호화나 운영 데이터 일괄 수정은 하지 않는다.
- G1은 팀장이 판정하고 Admin이 개발 담당자를 배정한다. G2는 요구자/오너/팀장, G3는 팀장 및 상 트랙 정보보호 지정 계정, G4는 오너/팀장이 각각 승인한다. 같은 사람이 두 역할을 맡아도 각 역할을 따로 확인한다.
- 역할은 로그인 계정과 DB 요구자/오너 ID, 팀장 역할, 지정 정보보호 ID로 확인한다. 클라이언트 승인 상태는 받지 않는다. 과제 행 잠금 안에서 검증/승인/단계 변경/감사 저장을 수행한다.
- G3는 기존 EVR 작성 완료와 ARD 기준 통과/금칙 위반 0건/근거 기록/요구자 UAT가 필요하다. G4는 파일럿 종료 기준과 결과 근거가 필요하다. EVP/EVR/DEP의 EVD 문서 통합은 이 변경에 포함하지 않는다.
- 보완은 다음 단계 이동을 막는다. 현재 승인 근거가 변경되면 현재 승인 라운드를 초기화하고 이전 라운드는 workflowApprovalHistory 및 감사 로그에 보존한다. 개발·평가 문서가 변경되면 UAT도 다시 확인한다.
- G1에서 하 트랙 판정과 담당자 배정이 완료되면 OPS 등록 대기로 이동한다. 오너/개발 담당/지식갱신 담당을 등록한 뒤 배포 완료할 수 있다. G2~G4는 적용 제외이며 승인 완료 레코드를 만들지 않는다.
- 기존 과제는 현재 위치와 과거 승인 이력을 유지한다. 이미 G1을 지난 과제를 일괄 단축 경로로 재배치하지 않는다. 이관 보완 중 부분 저장은 유지하고, 이관 완료 후 현재/후속 단계는 서버 승인 규칙을 적용한다.
- ARD를 승인 후 수정하는 정식 G2 재심사 화면과 EVD 통합은 별도 후속 작업이다. 승인 후 ARD를 무검증 변경해 기존 승인을 재사용하는 경로는 차단한다.
- 별도 DB 스키마 변경 없이 기존 raw_answers.portalState 및 gates/gate_approvals/document_versions/audit_logs에 저장한다.
